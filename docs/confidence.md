# 確度の設計（ルールの作成時と、ルールとの照合時）

この文書は、kagiya が結果に付ける「確度」を、だれが、いつ、何をもとに、どう決めるかを定める。
内容は、2026-11-14 から 2026-11-15 にかけて、利用者（このリポジトリの所有者）と開発者が 1 点ずつ確認して決めたものである。

**状態: この文書の内容は、まだ実装していない。** 現在の実装との違いは、7 章に書く。

## 1. この文書が定めること

kagiya は、ホストの設定ファイルと、導入されているソフトウェアの版を読み、あらかじめ作ってあるルールを当てはめて、
「そのサーバーが受け入れる設定になっている暗号の一覧」を求める。
この一覧が、どれだけ確かな根拠から求めたものかを、kagiya は「確度」として結果に付ける。

この文書は、次の 2 つの時点について、行う処理を定める。

- **ルールの作成時**: kagiya の開発者が、検証ラボでソフトウェアを測り、ルールを作る時点。
- **ルールとの照合時**: 利用者が kagiya を実行し、kagiya がホストを読んでルールを当てはめる時点。

## 2. 用語

この文書で使う言葉の意味を、次のとおりに定める。

| 言葉 | 意味 |
|---|---|
| 利用者 | kagiya を実行して、ホストの暗号を棚卸しする人 |
| 開発者 | kagiya のルールとプログラムを作る人 |
| 検証ラボ | 開発者が、公式のコンテナイメージに実物のソフトウェアを導入して動かす環境（`lab/`）。利用者のホストではない |
| 対象のソフトウェア | kagiya が設定を読む対象のソフトウェア（nginx、OpenSSL、JDK、WildFly など） |
| ルール | 開発者が検証ラボで確かめた事実を、対象のソフトウェアの版ごとに記録したデータ（`rules/` の YAML ファイル）。既定値の表、暗号の指定をスイートの一覧に直す対応表などがある |
| ルールの項目 | ルールの中の、1 つの事実（例: 「nginx 1.20.1 の既定の暗号の指定は `HIGH:!aNULL:!MD5` である」） |
| 出典 | ルールの項目に付ける、その事実を確かめた環境の記録（コンテナイメージのダイジェスト、OS の名前、注記） |
| 開発元の版 | 対象のソフトウェアの開発元が付けた版（例: パッケージの版 `1.1.1k-18.el8_6` のうち、`1.1.1k`） |
| 作り直しの番号 | ディストリビューションが、同じ開発元の版のパッケージを作り直すたびに進める番号（例: `1.1.1k-18.el8_6` のうち、`18`） |
| 系列 | ディストリビューションの種類と大きな版（例: `el8` は RHEL 8 系） |
| 配布元 | JDK を配っている組織（各ディストリビューション、Eclipse Temurin、Amazon Corretto など） |
| ハンドシェイク | TLS の接続を始める手順。クライアントが暗号スイートなどを提示し、サーバーが受け入れるかどうかを答える |
| 数え上げ | 検証ラボで、対象のソフトウェアをサーバーとして起動し、同じコンテナの中から、暗号スイート（またはプロトコル、鍵交換のグループ）を 1 つずつ提示してハンドシェイクを試み、サーバーが受け入れたものを記録すること |
| 実効値 | kagiya が、あるサーバーの 1 つの項目（暗号スイート、プロトコル、鍵交換のグループなど）について求めた、「受け入れる設定になっているもの」の一覧 |
| 確度 | kagiya が、実効値に付ける 3 段階の値（高・中・低）。その実効値を求めるのに使ったルールが、そのホストにどれだけ合っているかを表す |
| 不明 | kagiya が、実効値を求めず、求められなかった理由を記録すること。確度は付かない |
| 証明書の種類 | サーバーの証明書の鍵の種類。この文書では RSA と EC の 2 つを扱う |
| キーストア | 証明書と秘密鍵を 1 つのファイルにまとめたもの（PKCS#12、JKS など）。開くのにパスワードが要る |

## 3. 原則

利用者と開発者は、次の 3 つを原則として決めた。

1. **確度は、ルールとの照合時にだけ決まる。** ルールの作成時には、開発者は確度を決めない。
2. **開発者は、ルールに、確かめた事実と、その事実をどう確かめたかだけを書く。** 開発者は、確かめていないことをルールに書かない。
3. **確度を決める処理は、プログラムの 1 か所だけに置く。** 実効値を求める各処理は、確度を直接決めず、確度を決めるのに要る材料（4.2 節と 5.3 節）だけを渡す。

## 4. ルールの作成時に行うこと

### 4.1 だれが、どこで、何をするか

開発者が、検証ラボで、対象のソフトウェアの 1 つの版について、次の順に作業する。

1. 開発者は、公式のコンテナイメージに、対象のソフトウェアのその版を導入する。
2. 開発者は、その版について、ルールの項目にする事実を、4.2 節のいずれかの方法で得る。
3. 開発者は、得た事実が、その版そのものをサーバーとして起動して数え上げた結果と一致するかを確かめる（確かめない場合もある）。
4. 開発者は、得た事実をルールの項目として書き、出典に、事実を得た方法（`method`）と、数え上げで裏付けたかどうか（`verified-by-handshake`）を書く。

### 4.2 開発者が出典に書く 2 つの項目

開発者は、ルールの項目の出典に、次の 2 つを必ず書く。

**`method`（開発者が、その事実をどう得たか）**

| `method` の値 | 開発者が行ったこと | 例 |
|---|---|---|
| `enumerated-by-handshake` | 開発者が、対象のソフトウェアをサーバーとして起動し、数え上げを行って、その事実を得た | nginx が、DH パラメータの指定なしで DHE の暗号スイートを受け入れるかどうか |
| `reported-by-software` | 開発者が、対象のソフトウェア（そのコマンドや部品）を実行し、対象のソフトウェア自身が出力した値を、その事実とした。サーバーとして起動していたかどうかは問わない | `sshd -T` が出力した既定のアルゴリズムの一覧。`openssl ciphers` が出力した、暗号の指定に対応するスイートの一覧 |
| `read-from-distributed-files` | 開発者が、対象のソフトウェアの配布物（パッケージや JAR）の中のファイルや文字列を、対象のソフトウェアを実行せずに読み、その内容を事実とした | WildFly の JAR の中にある、暗号スイートごとの属性の表 |
| `read-from-upstream-source-code` | 開発者が、対象のソフトウェアの開発元が公開しているソースコードを読み、その内容を事実とした | WildFly の部品（Elytron）が暗号の指定を解釈する規則 |
| `read-from-upstream-documentation` | 開発者が、対象のソフトウェアの開発元が公開している資料（リリースノートなど）を読み、その内容を事実とした | 暗号ライブラリが、ある耐量子のアルゴリズムに対応した版 |

**`verified-by-handshake`（開発者が、その事実を数え上げで裏付けたか）**

| 値 | 意味 |
|---|---|
| `true` | 開発者が、その項目の値、またはその値を使って計算した結果が、**その版そのもの**をサーバーとして起動して数え上げた結果と一致することを確かめた |
| `false` | 開発者が、上の確認を行っていない。別の版で確認しただけの場合も `false` とする |

`method` が `enumerated-by-handshake` の項目は、数え上げそのもので得た事実なので、開発者は `verified-by-handshake` を必ず `true` と書く。

対象のソフトウェアの版を知る方法（パッケージの管理情報を読む、配布物のマニフェストを読む）は、どの項目でも同じなので、開発者は `method` に書かない。

### 4.3 数え上げを行わない版のルールに、開発者が書いてよいこと

開発者は、ある版について数え上げを行わず、`reported-by-software` や `read-from-distributed-files` の方法だけで、ルールの項目を作ってよい。
その場合、開発者は `verified-by-handshake` を `false` と書く。

ルールの項目には、性質の違う 2 種類がある。

| 種類 | 意味 | 例 |
|---|---|---|
| 値の項目 | 対象のソフトウェアが持っている値そのもの | nginx の既定の暗号の指定。sshd の既定のアルゴリズムの一覧 |
| 挙動の項目 | 対象のソフトウェアをサーバーとして起動し、設定を変えて試さないと分からない、振る舞い | nginx が、DH パラメータの指定なしで DHE の暗号スイートを受け入れるかどうか。WildFly が TLS 1.3 を受け入れる条件 |

開発者は、数え上げを行っていない版のルールに、値の項目だけを書く。
開発者は、数え上げを行っていない版のルールに、挙動の項目を書かない。別の版で数え上げて分かった挙動を、その版のルールに書き写すこともしない。

### 4.4 証明書の種類ごとの確認

サーバーが受け入れる暗号スイートは、サーバーの証明書の種類によって変わる。
検証ラボでは、開発者が証明書を自分で作ってサーバーに設定するので、開発者は証明書の種類を知っている。

開発者は、数え上げを行うとき、RSA の証明書を設定した場合と、EC の証明書を設定した場合の両方で数え上げる。
開発者は、DSA の証明書を設定した場合の数え上げは行わない（DSA の証明書は、現在ほとんど使われていないため）。

### 4.5 CI での検査

CI は、ルールのすべての出典に、`method` と `verified-by-handshake` が書かれていることを検査する。
CI は、どちらかが書かれていないルール、`method` が 4.2 節の 5 つの値のどれでもないルール、
`method` が `enumerated-by-handshake` なのに `verified-by-handshake` が `false` のルールを、不合格にする。

## 5. ルールとの照合時に行うこと

### 5.1 だれが、どこで、何をするか

利用者が、棚卸しの対象のホストで kagiya を実行する。kagiya は、次の順に処理する。

1. kagiya は、ホストに導入されている対象のソフトウェアの版を、パッケージの管理情報などから読む。
2. kagiya は、その版に当てはめるルールを探す（5.2 節）。
3. kagiya は、ホストの設定ファイルを読み、ルールを当てはめて、実効値を求める。
4. kagiya は、実効値を求めるのに使ったルールごとに、確度を決める（5.3 節）。
5. kagiya は、実効値と確度を、結果に書く。

### 5.2 kagiya が、当てはめるルールを探す方法

kagiya は、ホストに導入されている版について、次の順にルールを探す。

| 順 | kagiya が探すルール | この文書での呼び方 |
|---|---|---|
| 1 | ホストに導入されている版と、版の文字列が完全に同じ版のルール | 完全一致 |
| 2 | パッケージの名前、開発元の版、系列が同じで、作り直しの番号だけが違う版のルール | 補った（同じ系列） |
| 3 | 対象のソフトウェアが JDK の場合に限り、JDK のディレクトリにある `release` ファイルの版（`JAVA_VERSION`）が、ルールの JDK の表の開発元の版と完全に同じであるルール。配布元は違ってよい | 補った（配布元またぎ） |

kagiya は、上の 3 つのどれにも当てはまるルールがない場合、そのルールに頼る実効値を「不明」とし、推測では埋めない。

順 3 は、JDK だけに認める。kagiya は、JDK 以外の対象のソフトウェアに、順 3 を当てはめない。

### 5.3 kagiya が、確度を決める方法

kagiya は、実効値を求めるのに使ったルール 1 つについて、次の 2 つを材料として、確度を決める。

- kagiya が、そのルールを、5.2 節のどの順で見つけたか（完全一致か、補ったか）。
- そのルールの出典の `verified-by-handshake` が、`true` か `false` か。

| kagiya がルールを見つけた方法 | `verified-by-handshake` が `true` | `verified-by-handshake` が `false` |
|---|---|---|
| 完全一致 | 高 | 中 |
| 補った（同じ系列、または配布元またぎ） | 中 | 低 |

言葉で書くと、次のとおりである。

- **高**: kagiya が、ホストの版そのもののルールを使い、かつ、開発者がそのルールを数え上げで裏付けている。
- **中**: 「kagiya が、ホストの版そのものではないルールで補った」と「開発者がそのルールを数え上げで裏付けていない」の、どちらか一方だけが当てはまる。
- **低**: 上の 2 つが、両方とも当てはまる。

「補った（同じ系列）」と「補った（配布元またぎ）」は、確度を決めるうえで同じ扱いとする。

### 5.4 kagiya が、1 つの実効値に複数のルールを使った場合

kagiya は、1 つの実効値を求めるのに、複数のルールを使うことがある
（例: WildFly の暗号スイートは、WildFly の表と、WildFly を動かす JDK の表の両方を使って求める）。

この場合、kagiya は、使ったルールごとに 5.3 節の方法で確度を決め、そのうち最も低い確度を、その実効値の確度とする。
確度の高さは、高、中、低の順である。

### 5.5 kagiya が、アプリケーションを動かす JDK を 1 つに決められない場合

kagiya は、Java で動くサーバー（Spring Boot、WildFly など）について、起動の定義を読んでも、どの JDK で動くかを 1 つに決められないことがある。

この場合、kagiya は、ホストで見つけた JDK のそれぞれについて、その JDK で動くと仮定して、実効値と確度を求める。

- すべての JDK で実効値が同じになった場合、kagiya は、その実効値を結果に書く。確度は、JDK ごとに求めた確度のうち、最も低いものとする。
  kagiya は、JDK を 1 つに決められなかったこと自体を理由にして、確度を下げない。
  kagiya は、その実効値に、「見つけた JDK のどれで動いても同じ値である」ことを示す。
- JDK によって実効値が違った場合、kagiya は、その実効値を「不明」とする。

### 5.6 kagiya が、サーバーの証明書の種類を読めない場合

kagiya は、サーバーの証明書が PEM 形式のファイルで置かれている場合、そのファイルを読んで、証明書の種類を判定する。
kagiya は、サーバーの証明書がキーストアの中にある場合、キーストアを開かない（開くにはパスワードが要り、kagiya はパスワードを読まないため）。
そのため、kagiya は、証明書の種類を判定できない。

| kagiya が証明書の種類を判定できたか | kagiya が結果に書く実効値 |
|---|---|
| 判定できた | その種類の証明書で、サーバーが受け入れる暗号スイートの一覧 |
| 判定できなかった | 「RSA の証明書で受け入れる暗号スイート」と「EC の証明書で受け入れる暗号スイート」を合わせた一覧 |

kagiya は、証明書の種類を判定できなかった場合、合わせた一覧に、DSA の証明書でしか使えない暗号スイートを入れない
（開発者が、DSA の証明書での数え上げを行っていないため）。

kagiya は、証明書の種類を判定できなかったこと自体を理由にして、確度を下げない。
kagiya は、その実効値に、「証明書の種類によらず、受け入れうるものの一覧である」ことを示す。

証明書を必要としない暗号スイートの扱いは、この文書では変えない（現在の実装のままとする）。

### 5.7 kagiya が求めた実効値が、空の一覧になった場合

kagiya が設定をルールのとおりに解釈した結果、受け入れるものが 1 つも残らないことがある
（例: WildFly で、プロトコルを TLS 1.3 だけにし、TLS 1.3 用の暗号の指定を書いていない設定）。

この場合、kagiya は、空の一覧を実効値として結果に書く。
kagiya は、実効値が空であること自体を理由にして、確度を下げない。
kagiya は、その実効値に、「受け入れるものが 1 つもない設定である」ことを注記する。
レポートは、空の実効値を、利用者が見落とさない形で表示する。

## 6. 確度が表すことと、表さないこと

確度が表すのは、「kagiya が実効値を求めるのに使ったルールが、そのホストにどれだけ合っているか」だけである。

| 確度が「高」のときに言えること | 確度が「高」でも言えないこと |
|---|---|
| kagiya は、そのホストに導入されている版そのものについて、開発者が数え上げで裏付けたルールを使った | 実効値が、そのサーバーが実際に受け入れるものと、過不足なく一致すること |

実効値が、実際に受け入れるものより広い場合があることは、確度ではなく、実効値に付ける表示（5.5 節、5.6 節）で、kagiya が利用者に伝える。

## 7. 現在の実装との違い

| 項目 | 現在の実装 | この文書の設計 |
|---|---|---|
| ルールの出典 | 事実を得た方法は、注記の文章にだけ書かれている。`method` と `verified-by-handshake` はない | 開発者が、すべての出典に `method` と `verified-by-handshake` を書く |

## 8. 実装するときに行う作業

1. 開発者は、既存のルールのすべての出典に、`method` と `verified-by-handshake` を付ける。
   開発者は、手で付けず、ルールを作った検証ラボの生成スクリプトに出力させて、ルールを作り直す。
2. 開発者は、確度を決める処理を、プログラムの 1 か所にまとめる。実効値を求める各処理が確度を直接決めていないことを、CI で検査する。
3. 開発者は、結果の形式とレポートに、確度「低」と、5.5 節・5.6 節・5.7 節の表示を加える。
4. 開発者は、4.5 節の CI での検査を加える。

# kagiya の限界（免責事項のもと）

kagiya が**保証しないこと・分からないこと・見ていないもの**の一覧。
利用者向けの免責事項を書くときの材料として、実装や実物確認の過程で分かったことを随時追記する。

- 「恒久」: 設計上の方針によるもので、今後も変わらない。
- 「現時点」: まだ実装・確認していないだけで、今後解消する予定があるもの。

最終更新: 2026-11-14（Java / Tomcat の対応、JAR の中の同梱ライブラリの棚卸しまで）

---

## 1. 「通信しない」ことの保証範囲

| 限界 | 区分 | 説明 |
|---|---|---|
| 保証するのは本プロセスの挙動まで | 恒久 | 保証するのは「本プロセスが通信用の機能を使わない」「ネットワーク越しのファイルシステム（NFS、SMB など）と、開くと取得が発生するファイルに触れない」こと。次のものは検出も制御もできない: ブロックレベルのネットワークストレージ（iSCSI、SAN など）上のローカルファイルシステム、アンチウイルス・EDR によるクラウド照会、OS の監査ログの転送など、第三者による間接的な通信 |
| マウント表の取得後に現れたマウント | 恒久 | スキャン中に新しくマウントされたネットワークファイルシステムは、開いた後のデバイス番号の照合で検出して読まないが、ディレクトリを開く操作そのものは発生し得る |
| 走査中にディレクトリが差し替えられた場合 | 現時点 | 走査中のディレクトリが、確認の直後に同じ場所でシンボリックリンクへ差し替えられると、その行き先のディレクトリを開いてしまうことがある（開いた後の照合で検出して中身は読まないが、開く操作そのものは発生し得る。行き先がネットワークファイルシステムなら通信になる）。スキャン対象のディレクトリに書き込める利用者が、タイミングを合わせて行う必要がある。リンクを辿らない方法でディレクトリを開く実装に置き換える予定 |
| 実行時の封じ込めはベストエフォート | 恒久 | Linux の seccomp は、適用できない環境（古いカーネル、既存のサンドボックス内、エミュレーション環境）では適用されないまま処理を続ける。適用の成否は結果に記録する。主たる保証は「通信コードを持たない」こと |
| Windows での封じ込め | 現時点 | 未実装 |

## 2. 見ていないもの（探索範囲）

| 限界 | 区分 | 説明 |
|---|---|---|
| ネットワークファイルシステム上のファイル | 恒久 | 読まない（スキップとして記録する）。そこにある証明書・鍵・設定は結果に現れない |
| 種別が不明なファイルシステム | 恒久 | 分類表にない種別は安全側に倒して読まない。コンテナのバインドマウントや独自のファイルシステムが該当し得る |
| シンボリックリンクの先 | 恒久 | 探索ではリンクを辿らない。リンク経由でしか到達できない場所にあるファイルは見つからない（共有ライブラリと証明書ストアの特定では、安全を確認しながら辿る） |
| 既定の探索起点の外 | 恒久 | 既定では `/etc`、`/opt`、`/usr/local`、`/srv`、`/var/www`、`/root` と証明書ストアの場所だけを探す。`/home` やその他の場所は、指定しない限り見ない |
| 名前や拡張子から鍵素材と分からないファイル | 恒久 | 候補は拡張子・ファイル名で選ぶ。拡張子のないファイルは 16 KiB 以下のものだけ中身を見る。独自の名前・拡張子で置かれた大きな鍵ファイルは見つからない |
| 大きすぎるファイル、深すぎる階層 | 恒久 | 上限（既定で 64 MiB、64 階層）を超えるものは読まない（スキップとして記録する） |
| 読み取り権限のないもの | 恒久 | 記録して先へ進む。一般ユーザーで実行した場合、秘密鍵や一部の設定は見えない。権限を迂回する操作は行わない |
| コンテナの中、コンテナイメージ | 現時点 | ホストからコンテナ内部やイメージ層は調べない。コンテナ内で kagiya を実行することはできる |
| 他のマウント名前空間 | 恒久 | 自プロセスから見えるファイルシステムだけが対象 |
| ハードウェア（HSM、TPM）内やメモリ上の鍵 | 恒久 | 対象外 |

## 3. 中身を確認できないもの

| 限界 | 区分 | 説明 |
|---|---|---|
| パスワードで保護されたキーストア・秘密鍵の中身 | 恒久 | パスワードは一切使わない。暗号化された PKCS#12 の中の証明書などは「確認できない」と記録するにとどまる。最近の Java の既定のキーストア形式（PKCS#12）は証明書も暗号化するため、中身が見えないものが多い |
| 公開成分を含まない秘密鍵と、証明書との対応 | 恒久 | 秘密成分を使った計算は行わない。OpenSSL が出力する Ed25519 や DSA（PKCS#8）の秘密鍵、暗号化された秘密鍵は、公開鍵の指紋が得られず、証明書や SSH 公開鍵と対応づけられない |
| JCEKS の共通鍵エントリ以降 | 現時点 | 共通鍵エントリに出会うと、そこで読み取りを打ち切る（「途中まで読んだ」と記録する） |
| Bouncy Castle 形式のキーストア | 恒久 | BKS は、証明書のエントリをパスワードなしで読める（鍵のエントリは暗号化されており、数だけ記録する）。UBER と BCFKS は全体が暗号化されているため、形式を見分けて「中身を確認できない」と記録するにとどまる（BCFKS は保護の方式だけ読む）。形式は、実物の Bouncy Castle（bcprov-jdk18on 1.87）で作ったキーストアで確かめた。拡張子が `.bks` / `.uber` / `.bcfks` / `.bcfips` / `.fks` と、これまでのキーストアの拡張子のファイルが対象で、それ以外の名前のものは見つけない |
| JAR に同梱された暗号ライブラリ | 恒久 | 探索で見つかった `.jar` / `.war` / `.ear` の中身の一覧を読み、同梱ライブラリの置き場（`BOOT-INF/lib/`、`WEB-INF/lib/`、`lib/`）にある JAR の名前から、Bouncy Castle、Conscrypt、Netty の tcnative、組み込みの Tomcat と、その版を記録する。分かるのは「置かれている」ことまでで、アプリが実際に使っているか、どの機能を呼んでいるかは分からない。名前を変えて置かれたもの、ほかのライブラリの中に取り込まれたもの（シェーディング）、入れ子の JAR のさらに中にあるものは見つけない。開く JAR は 1 回のスキャンで 2,000 個までで、超えた分は読み飛ばしたことを記録する |。Windows での動作は確かめていない（このコレクタのテストは、ほかのコレクタと同じく unix だけで動かしている）
| 未対応の形式 | 現時点 | PGP 鍵、PuTTY の PPK、NSS のデータベース、BKS キーストアは未対応 |
| カタログにないアルゴリズム | 恒久 | 「未知」として記録する。評価（危殆化、量子耐性）は付かない |

## 4. 「使われているか」について

| 限界 | 区分 | 説明 |
|---|---|---|
| 実際にネゴシエーションされている暗号 | 恒久 | 設定から分かるのは「許可・提示されている」ものまで。相手との間で実際にどれが選ばれているかは、通信を観測しないと分からない |
| 「有効」と「稼働中」の差 | 恒久 | 起動するよう設定されていても止まっていることがあり、手動起動やソケット起動で動いていることもある。稼働中かどうかは、明示的に指定した場合（`--process-info`）にだけ調べる |
| クライアントとしての利用 | 恒久 | 定期実行されるスクリプトなどからの利用は、サービスとしては見えない |
| ソースコードと本番の関係 | 恒久 | ソースコードに書かれた処理が、本番で動いているとは限らない |
| ログに残る実績 | 恒久（v1） | ログは読まない |
| 証明書の信頼性・有効性 | 恒久 | 署名の検証、信頼の連鎖の検証、失効の確認は行わない（通信が発生し得るため）。記録するのは証明書に書かれた内容 |

## 5. 版と既定値の特定について

### 5.1 ソフトウェアと版の特定

| 限界 | 区分 | 説明 |
|---|---|---|
| 環境変数による差し替え | 恒久（既定） | `LD_LIBRARY_PATH`、`LD_PRELOAD`、`OPENSSL_CONF` などによるライブラリや設定の差し替えは分からない。稼働中プロセスの環境変数は読まない |
| 実行時に読み込まれるモジュール | 恒久（既定） | ルールに定義したもの（Apache の `mod_ssl.so` など）以外の、実行時に読み込まれるモジュールやプラグインは分からない |
| 静的リンクされた暗号ライブラリ | 現時点 | 共有ライブラリとしてリンクされているものだけを特定する |
| コンポーネントとパッケージの対応 | 現時点 | 名前による推定。同じライブラリの複数の版が導入されている場合、対応を誤る可能性がある |
| パッケージ管理外で導入されたソフトウェア | 恒久 | パッケージの版は付かない。バイナリに埋め込まれた版文字列だけが手がかりになる |
| 更新途中のパッケージ管理データベース | 恒久 | コマンドを使わずファイルを直接読むため、更新の最中は整合しない部分を読み飛ばすことがある（件数を記録する） |
| 未対応のパッケージ管理形式 | 現時点 | rpm の NDB 形式（SUSE 系）は未対応 |
| 実物で確認していないディストリ・版 | 恒久 | ルールの既定値や対応表は、出典として記録したイメージ・パッケージ版で確認したもの。それ以外の環境では、値が当てはまらない可能性がある（信頼度を下げて記録する） |
| RHEL の確認範囲 | 恒久 | Red Hat Universal Base Image とそのリポジトリの範囲で確認している |
| ビルド時に決まる既定値 | 現時点 | OpenSSL のセキュリティレベルの既定は、暗号スイートの対応表（パッケージ版ごとの実測）から、nginx と Apache の暗号スイートの実効値に反映している。鍵交換のグループの既定（ライブラリの既定と、stunnel 自身の既定）も、パッケージ版ごとの実測の表から反映している。それ以外の、設定ファイルに現れない既定値（署名アルゴリズムなど）は、まだ結果に反映していない |
| RHEL 系の一部のアプリは AlmaLinux で測っている | 恒久 | UBI のリポジトリにないアプリ（PostgreSQL など）の RHEL 系の既定値は、AlmaLinux の公式イメージで測った。出典にそのイメージを記録している。RHEL のパッケージと版の文字列が同じ場合（例: `postgresql-server 13.23-6.el9_8`）は、その表を RHEL にも使う。RHEL そのものでの実測ではない。版の文字列が違う場合（AlmaLinux 8 のモジュールのパッケージなど）は、RHEL では「不明」になる |
| 既定値表・対応表にないパッケージ版 | 恒久 | 記載のない項目の実効値は、導入されているパッケージ版に対応する実測の表がある場合にだけ求める。表にない版（未採取のディストリ・版、独自ビルドなど）では「不明」とし、推測では埋めない。パッケージ名・上流の版・ディストリの系列が同じでリリース番号だけが違う版（エラータ）に限り、実測した版の表で補間する（sshd・nginx・Apache の既定値表と、OpenSSL の暗号スイートの対応表のいずれも）。補間した結果には、実測した版と導入されている版を注記に残し、確度を一段下げる。リリースの違いで既定値が変わっていた場合、補間した値は実際と異なる |
| パッケージの更新で既定値表が古くなる | 恒久 | ディストリがパッケージを更新すると、版の文字列が変わり、表と完全には一致しなくなる。リリースだけの違いなら補間で求まるが（確度は一段下）、上流の版が変わると「不明」になる。表は、採取し直して更新する必要がある（採取は自動化しておらず、必要なときに手動で行う） |
| 複数の版の OpenSSL | 現時点 | 対応表のある OpenSSL のパッケージが複数導入されている場合、そのサーバーがどれを使うかを決められないため、暗号スイートの実効値は「不明」とする |
| 独自にビルド・改変されたソフトウェア | 恒久 | ビルド時のオプションや独自のパッチによる既定値の違いは分からない |

### 5.2 OS とライブラリの設定

| 限界 | 区分 | 説明 |
|---|---|---|
| OS 暗号設定の対応範囲 | 現時点 | 読むのは、システム全体の暗号ポリシーの名前、カーネルの FIPS モード、OpenSSL のシステム既定の TLS 設定まで。GnuTLS、NSS、Kerberos、Java、libssh などの設定は未対応 |
| OpenSSL 設定ファイルの変数 | 恒久 | 設定ファイル中の変数（`$var`、`$ENV::NAME`）は展開しない。変数を含む値は「解釈しなかった」と記録し、値としては採らない |
| OpenSSL 設定ファイルの相対パスの取り込み | 恒久 | `.include` が相対パスの場合は辿らない（基準となるディレクトリが実行時の環境で決まるため） |
| カーネルの FIPS モード | 現時点 | 読み取りは実装したが、実物（FIPS モードのホスト）では未確認。検証に使ったコンテナには該当のファイルがなかった |
| システムの OpenSSL 設定の値を読めなかった場合 | 恒久 | システムの openssl.cnf の値は、想定した文字だけからなるものに限って記録する。記録しなかった項目（`CipherString`、`Ciphersuites`、`Groups`）があるときは、「指定なし」とは扱わず、それに依存する実効値を「不明」にする |
| システムの OpenSSL 設定の適用 | 恒久 | セキュリティレベルと TLS 1.3 のスイートは、システムの openssl.cnf（RHEL 系では暗号ポリシーが生成した内容）の既定が、そのサーバーに適用される前提で求める。環境変数（`OPENSSL_CONF`）で別の設定ファイルに差し替えられている場合や、アプリが設定の読み込みを無効にしている場合は当てはまらない |

### 5.3 設定の読み取りと実効値（アプリ共通）

| 限界 | 区分 | 説明 |
|---|---|---|
| 記録する設定項目 | 恒久 | 設定ファイルから記録するのは、ルールで許可した項目だけ。それ以外の項目は「記録対象外」として件数だけ残す |
| 実効値を求められるアプリと項目 | 現時点 | 実効値（設定の記載と既定値から求めた、受け入れる方式の一覧）を求めるのは、sshd の各アルゴリズムの一覧と、nginx・Apache httpd・HAProxy・stunnel・Postfix（受信側の smtpd）・PostgreSQL・Dovecot・MariaDB・MySQL の暗号スイート（TLS 1.2 以下と TLS 1.3）と、受け入れる鍵交換のグループ。プロトコル、署名アルゴリズムは、設定に明記された値の記録まで |
| 鍵交換のグループの実効値の意味 | 恒久 | 「サーバーが受け入れる設定になっているグループ」の一覧で、TLS 1.2 と TLS 1.3 を分けていない（有限体 DH と ML-KEM 系は TLS 1.3 でだけ使われる）。実際にどのグループで鍵交換が行われるかは、接続してくるクライアントが何を提示するかで決まる。耐量子のハイブリッドが一覧にあっても、クライアントが対応していなければ従来の方式で接続される。従来のグループが一覧に残っている限り、そのような接続は拒否されない |
| 鍵交換のグループを求められない場合 | 現時点 | OpenSSL 1.0.2（Ubuntu 16.04 など）は実測の表がなく「不明」。nginx の `ssl_conf_command` がある範囲は求めない。Apache の `SSLOpenSSLConfCmd` は `Groups` / `Curves` だけを読む。OpenSSL 以外のライブラリ（GnuTLS、NSS など）を使うサーバーは対象外（Java は、JDK の既定だけを別に求める） |
| 起動できない設定 | 恒久 | 設定の誤りでサーバーが起動しない場合（JDK が対応するスイートが 1 つも残らない暗号指定など）でも、設定から求めた値を出すことがある。起動できるかどうかは判断していない |
| 設定が受け付けられるかは確かめない | 恒久 | kagiya は、設定がそのアプリの版に受け付けられるかを確かめない。たとえば HAProxy 1.8 / 2.0 は `ssl-default-bind-curves` を受け付けず起動に失敗するが（実測）、kagiya は書かれた値から実効値を求める。起動できない設定に対する結果は意味を持たない |
| 対応しているアプリの設定 | 現時点 | 設定値を読むのは OpenSSH サーバー（sshd）、nginx、Apache httpd、HAProxy、stunnel の5つ。その他のアプリは未対応 |
| OpenSSL の設定を直接変える書き方 | 現時点 | nginx の `ssl_conf_command`、Apache の `SSLOpenSSLConfCmd` が書かれている範囲は、暗号文字列だけでは結果が決まらないため、暗号スイートの実効値を「不明」とする。Apache の `SSLCipherSuite TLSv1.3 ...`（TLS 1.3 のスイートをアプリの設定で指定する書き方）は、TLS 1.3 の側だけ「不明」とする。Apache の `mod_md`（証明書の自動取得）や `mod_gnutls` の設定は記録していない |
| 暗号スイートの実効値が示す範囲 | 恒久 | 示すのは「そのサーバーが受け入れ得るスイートの集合」。どのプロトコル（TLS 1.0〜1.3）が有効かは、まだ解決していない（TLS 1.3 のスイートは「TLS 1.3 が有効な場合に使われるもの」として別の項目で示す）。並びは暗号文字列の展開順で、サーバーの優先順として実際に使われるかは設定（`ssl_prefer_server_ciphers`、`SSLHonorCipherOrder`）による。実測で確かめたのは集合の一致までで、優先順は測っていない |
| 暗号スイートの絞り込みの前提 | 恒久 | 事前共有鍵（PSK）と SRP のスイートは、アプリ側の追加の設定がないと使えないため、使えないものとして扱う（Apache で SRP を設定している場合は当てはまらない）。証明書の種類は、設定が指す証明書ファイルの先頭の証明書から判定する。証明書を読めない場合（権限がない、まだ作られていない、変数を含む指定など）は、種類による絞り込みをせずに求め、確度を一段下げる。証明書の鍵長や署名がセキュリティレベルを満たすか（満たさないとサーバーは起動できない）は確認していない |
| DHE を使えるかの判定 | 現時点 | nginx は `ssl_dhparam` の指定があれば使えるとし、なければ版ごとの実測（古い版は組み込みのパラメータを持つ）に従う。Apache は組み込みのパラメータで使えるとする（証明書ファイルに付けた独自のパラメータや、鍵長とセキュリティレベルの関係は見ていない）。その版の実測がなければ、DHE のスイートを残したまま確度を一段下げる |
| OpenSSL の暗号文字列で展開しない書き方 | 恒久 | `SUITEB128` などの特別な語は展開しない（「不明」とする）。その版が知らない語は、OpenSSL と同じく無視する |
| 条件付きの設定 | 恒久 | sshd の Match ブロックの中の設定は「条件付き」として記録する。どの接続に適用されるかは判定しない |
| systemd の上書き設定 | 現時点 | ユニットの一部だけを上書きするドロップイン（`<ユニット名>.d/*.conf`）は読んでいない。そこで起動引数や環境ファイルが変えられている場合は反映されない |
| systemd 以外の起動方法 | 現時点 | サービスの有効化状態は systemd の定義から読む。SysV init のスクリプト、コンテナの起動コマンド、手動起動は分からない |
| 設定ファイルの場所の指定 | 現時点 | 起動引数で設定ファイルの場所が変えられている場合（sshd の `-f` など）は追っていない |
| 秘密鍵と対になる公開鍵ファイル | 現時点 | 設定から参照されている秘密鍵には利用の確からしさが付くが、同じ場所にある対の公開鍵ファイル（`*.pub`）には付かない |
| 設定中のアルゴリズム名と暗号カタログ | 現時点 | 設定に書かれた SSH のアルゴリズム名は文字列として記録するだけで、暗号カタログの資産とは結び付けていない（評価の対象にまだならない） |

### 5.4 OpenSSH（sshd）

| 限界 | 区分 | 説明 |
|---|---|---|
| sshd の実効値で解決しない書き方 | 恒久 | ワイルドカードを含む追加・先頭指定（`+...*`、`^...*`）と、ワイルドカードを含む一覧の明記は、その版が対応する全アルゴリズムの一覧が要るため「不明」とする（削除でのワイルドカードは解決する） |
| sshd の条件付きの設定と実効値 | 恒久 | 実効値は、全体に適用される設定から求める。Match ブロックの中の設定による接続ごとの違いは反映しない |

### 5.5 nginx・Apache httpd

| 限界 | 区分 | 説明 |
|---|---|---|
| nginx・Apache の階層間の引き継ぎと上書き | 現時点 | 外側の値が内側に引き継がれる規則を解決しているのは、暗号スイート（nginx の `ssl_ciphers`、Apache の `SSLCipherSuite`）、証明書、DH パラメータの指定だけ。それ以外の項目は、書かれている範囲（http 全体、どの server / VirtualHost）とともに記録するにとどまる。nginx の `stream` / `mail` の中の server は、引き継ぎの確認をしていない |
| nginx・Apache の設定中の変数 | 恒久 | 変数を含むパス（nginx の `$変数`、Apache の `${変数}`）は、どのファイルかを確定できないため記録しない（「解釈しなかった」として件数に残す）。Debian 系の Apache は、ログの場所などに環境変数を使っている |
| nginx の古い書き方 | 現時点 | TLS を使う待ち受けは `listen ... ssl` の形で判定する。古い書き方（`ssl on;`）は TLS の待ち受けとして認識しない |
| Apache のモジュールの判定 | 恒久 | `<IfModule>` の条件は、設定ファイル中の LoadModule の記載から判定する。本体に組み込まれたモジュールは分からないため、その条件の中身は採らない |
| Apache の起動時の指定 | 恒久 | `<IfDefine>` の条件は、起動時の指定（`-D`）が分からないため、定義されていないものとして扱う |
| Apache のディレクトリ単位の設定 | 恒久 | `.htaccess` は読まない。ディレクトリを指定した Include は、その直下のファイルだけを読む |
| Apache の待ち受けポート | 現時点 | 記録する Listen は、TLS を有効にした `<VirtualHost>` と同じポートのものと、`https` の指定があるものだけ |
| Debian 系の Apache の組み込みの既定 | 現時点 | Debian・Ubuntu の Apache は、パッケージの設定ファイルが必ず `SSLCipherSuite` を書いているため、mod_ssl に組み込まれた既定の暗号文字列を実測できていない。その記載を消した構成では、暗号スイートの実効値は「不明」になる |
| 同じ名前の server / VirtualHost | 現時点 | 実効値は範囲の名前（最初の `server_name`、VirtualHost の宛先）で区別する。同じ名前の範囲が複数あると、結果の上で区別が付かない |
| Apache のディレクトリ単位の暗号指定 | 恒久 | `<Directory>` や `<Location>` の中の `SSLCipherSuite`（接続後の再ネゴシエーションで適用される）は、暗号スイートの実効値に反映しない |

### 5.6 HAProxy・stunnel

| 限界 | 区分 | 説明 |
|---|---|---|
| HAProxy の証明書の選ばれ方 | 恒久 | HAProxy は、サーバー名（SNI）のない接続には最初の証明書だけを使う。実効値は「指定されたどの証明書も選ばれ得る」前提の集合で、サーバー名を付けない接続で受け入れられる集合より広いことがある。証明書をディレクトリや一覧ファイル（`crt-list`）で指定している場合は、どの証明書が使われるかを追わず、種類による絞り込みをしない（確度は一段下） |
| HAProxy の設定で見ていないもの | 現時点 | 実効値を求めるのは、frontend / listen の `bind` の待ち受けだけ。`defaults` の節の値の引き継ぎ、backend の `server` 行（外向きの接続）の暗号指定、`ssl-default-bind-options` や `ssl-min-ver` によるプロトコルの制限は、記録するか未対応のいずれかで、実効値には反映していない。証明書に付けた DH パラメータも見ていない |
| HAProxy が読む設定ファイル | 現時点 | 読むファイルは、ユニットの起動コマンドの `-f` の指定に従う（なければ `/etc/haproxy/haproxy.cfg` だけ）。複数のファイルにまたがる節の続き方は実物で確かめていない（ファイルごとに節が始まるものとして読む）。環境変数を含む行は値を展開せず、その行の指定は採らない |
| stunnel の設定で見ていないもの | 現時点 | 実効値を求めるのは、待ち受ける側のサービスだけ。外向きの接続をするサービス（`client = yes`）は設定の記録まで。`include` で取り込まれる設定、相対パスで書かれた証明書、`sslVersion` などによるプロトコルの制限、PSK の設定（`PSKsecrets`。指定があると PSK のスイートも使える）は実効値に反映していない |
| stunnel の起動単位と有効化の状態 | 現時点 | `/etc/stunnel/*.conf` をすべて読み、どれも設定として扱う。どの設定ファイルで実際に起動されるか（`stunnel@名前.service` の有効化、Debian 系の `/etc/default/stunnel4`）は見ていない |

### 5.7 Postfix・Dovecot

| 限界 | 区分 | 説明 |
|---|---|---|
| Dovecot で扱う範囲 | 現時点 | 範囲は「全体」と、TLS の指定を上書きしている（または chroot を外している）プロトコルごと。接続先の名前や接続元ごとの設定（`local_name`、`local`、`remote` の入れ子）の中に TLS の指定があると、実効値は「不明」になる。設定に直接書かれた証明書（`<ファイル` でない値）は、種類による絞り込みをしない。待ち受けごとの TLS の有無（`inet_listener` の `ssl`）と、STARTTLS か最初から TLS かは区別していない |
| Dovecot の chroot と暗号ポリシー | 恒久 | RHEL 系の `PROFILE=SYSTEM` が chroot の中でライブラリの既定になることは、AlmaLinux 8 / 9 / 10 のコンテナで実測した。kagiya は、接続を受けるサービス（`service <プロトコル>-login`）の `chroot` が空に設定されているかどうかだけを見て判断する。それ以外の方法で chroot の中に暗号ポリシーのファイルを置いている環境では、実際と異なる |
| Postfix で扱う範囲 | 現時点 | 実効値を求めるのは、master.cf の、種類が inet でプログラムが smtpd のサービス（受信側）だけ。送信側（smtp、lmtp）、postscreen、tlsproxy、サーバー名ごとの証明書（`tls_server_sni_maps`）、接続元ごとの方針は、設定に書かれた値の記録まで。`smtpd_tls_chain_files` を使っている場合は、証明書の種類による絞り込みをしない（確度が一段下がる） |
| Postfix の設定の読み方 | 恒久 | main.cf と、同じディレクトリの master.cf を読む。複数インスタンス（`multi_instance_directories`）と、起動時に `-c` で指定された別の設定ディレクトリは読まない。値の中の参照は `$名前`、`${名前}`、`$(名前)` を展開する。条件つきの書き方（`${名前?値}`、`${名前:値}`）と、既定値を測っていない項目への参照があると、その項目に依存する実効値は「不明」になる |
| Postfix の除外の指定の区切り | 現時点 | `smtpd_tls_exclude_ciphers` などの除外の指定は、カンマと空白で区切られたものとして読む（実測したのはこの書き方だけ）。それ以外の文字を含む指定は「不明」にする |

### 5.8 PostgreSQL・MariaDB・MySQL

| 限界 | 区分 | 説明 |
|---|---|---|
| PostgreSQL で扱う範囲 | 現時点 | クラスタが複数ある場合（Debian 系の `/etc/postgresql/<版>/<クラスタ>/`）は、名前の順で最初のものだけを読む。起動時の引数で指定された設定（`-c`、`-D`）と、RHEL 系で既定以外の場所に置かれたデータディレクトリは読まない。PostgreSQL 18 の `ssl_groups`・`ssl_tls13_ciphers` は実測しておらず、指定があるとその項目は「不明」になる。`ssl_min_protocol_version` によるスイートの絞り込みはしていない。Ubuntu 16.04 の PostgreSQL 9.5 は測れておらず「不明」 |
| MariaDB / MySQL で扱う範囲 | 現時点 | 設定ファイルは `/etc/my.cnf` か `/etc/mysql/my.cnf` の、先に見つかったほうから読む（両方ある場合に両方が読まれる構成、起動時の引数で指定された設定、利用者ごとの `~/.my.cnf` は読まない）。版ごとのグループ（`[mysqld-8.0]` など）は読まない。測れていない版（Ubuntu 16.04 / 20.04 の MariaDB、Ubuntu 16.04 の MySQL 5.7、OpenSSL 以外のライブラリでビルドされたもの）は「不明」。`tls_version` によるスイートの絞り込みはしていない。MySQL 8.4 が拒否する暗号を設定に書いた場合（起動できない設定）でも、書かれた値から求める |
| MySQL の既定の暗号の並び | 恒久 | MySQL の既定の並びはサーバーの変数に現れないため、実行ファイルに埋め込まれた並びを組み合わせ、実測（受け入れたスイート）と一致するものを採っている。受け入れるスイートの集合は実測と一致するが、優先順は確かめていない |

### 5.9 Java（JDK）

| 限界 | 区分 | 説明 |
|---|---|---|
| Java（JDK）で求めるのは「JDK の既定」まで | 現時点 | 導入されている JDK（ディストリの OpenJDK 8 / 11 / 17 / 21 / 25）ごとに、アプリが何も指定しない場合に受け入れるプロトコル・暗号スイート・鍵交換のグループを求める。Java で書かれたサーバーが自分の設定で選んだ値は、パッケージで導入した Tomcat についてだけ別に求める（下の Tomcat の項目）。Spring Boot などは、まだ読まない |
| Java の起動時の指定は読まない | 恒久 | Java は、起動時の指定（`-Djdk.tls.namedGroups`、`-Djdk.tls.server.protocols`、`-Djava.security.properties=<別の設定ファイル>`、RHEL 系の `-Dredhat.crypto-policies=false` など）で TLS の既定を変えられる。kagiya は動いているプロセスを見ないので、これらは反映されない。結果は「配られた設定ファイルのとおりに動いている場合」の値 |
| Java で求めない場合 | 現時点 | 次の場合は「不明」とし、理由を残す。実測の表になく、開発元の版が同じ表もない JDK。カーネルが FIPS モードの場合（RHEL 系の JDK は別の暗号の実装に切り替わる。その状態は測っていない）。`java.security` に、その版で確かめていないつなぎ方（`include`、`security.useSystemPropertiesFile`）がある場合。`jdk.tls.disabledAlgorithms` の記載がない場合。鍵交換のグループだけは、確かめていない書き方（`keySize <=` など、`<` 以外の鍵長の条件）があると求めない |
| Java の一覧の意味 | 恒久 | 暗号スイートの一覧は「JDK が既定で有効にするもの」で、サーバーが持つ鍵の種類による絞り込みはしていない（DSA の鍵がなければ `DHE_DSS` のスイートは実際には選ばれない）。鍵交換のグループは、制限をすべて外した状態で受け入れたものを土台にしており、既定では受け入れないが名前を挙げれば使えるグループ（`jdk.tls.namedGroups` で足すもの）は分からない。Java 8 は、クライアントが有限体 DH のグループを示さない場合、DHE に 1024 ビットのパラメータを使う（実測。結果に注記する） |
| 配布元の違う JDK は、開発元の版が同じ表で補っている | 恒久 | ディストリのパッケージ以外の JDK（Temurin、Corretto、Zulu、Oracle JDK など）や、測っていないディストリの JDK は、JDK のディレクトリにある `release` ファイルの版（`JAVA_VERSION`）が、測定した表の版と完全に一致する場合に、その表で補う（確度を下げ、注記を付ける）。「開発元の版が同じなら中身は同じ」ことは、Temurin 8 / 11 / 17 / 21 / 25 と Corretto 8 / 17 / 21 で確かめたが、それ以外の配布元では確かめていない。配布元が独自に実装を変えている場合（独自の暗号プロバイダを既定にしている製品など）は、結果が実際と違う可能性がある。この補い方は Java だけのもので、ほかのソフトウェアでは行わない |
| JDK を探す場所 | 現時点 | `/usr/lib/jvm/<名前>/` と `/opt/java/openjdk`（Temurin の公式イメージの配置）だけ。それ以外の場所に展開された JDK（`/opt/<製品>/jre` など、アプリに同梱されたものを含む）は見つけない |
| Java の RHEL 系は AlmaLinux で測っている | 恒久 | RHEL 系の OpenJDK の表は、AlmaLinux 8 / 9 / 10 の公式イメージで測った（出典に記録）。RHEL のパッケージとリリースの文字列が違えば、補間（確度を下げる）か「不明」になる |
| Java のセキュリティプロバイダ | 現時点 | `java.security` に、JDK に含まれないプロバイダ（BouncyCastle、Conscrypt など）や、TLS の実装を差し替える設定（`ssl.ServerSocketFactory.provider` など）があると、JDK の表を当てはめず「不明」とする。JDK に含まれるプロバイダの名前は、測った 35 の JDK の既定に現れたものに限っているので、それ以外の名前（測っていない配布元の独自のプロバイダなど）も「不明」になる。プログラムの中で実行時に足されるプロバイダは分からない |

### 5.9.1 暗号ライブラリが耐量子のアルゴリズムに対応している版

| 限界 | 種別 | 内容 |
|---|---|---|
| 「対応」の意味 | 恒久 | ライブラリがその方式を持っている、という意味。アプリが使っているか、使う設定になっているかは分からない（TLS の鍵交換は、各ソフトの実効値で見る） |
| 対象のライブラリ | 現時点 | OpenSSL、Bouncy Castle（本体・TLS・FIPS 版）、Conscrypt、Netty tcnative（BoringSSL を含むもの）だけ。JDK そのものが持つ耐量子のアルゴリズム、GnuTLS、NSS、wolfSSL などは対象外。Bouncy Castle のうち、本体と TLS 以外の成果物（bcpkix など）、FIPS 版の TLS（bctls-fips）には何も付けない |
| 版はファイル名から | 恒久 | Java のライブラリの版は、JAR のファイル名から読む。名前を変えて置かれたもの、版のない名前、正式版でない版（alpha、RC、SNAPSHOT）は「不明」になる。別の名前で作り直された JAR（アプリに取り込んで再配布したもの）は、ライブラリとして拾えない |
| 測っていない組み合わせ | 現時点 | 測ったのは arm64 の Linux。Bouncy Castle は jdk18on 向けだけ（jdk15on などは、同じ版なら同じと見なす）。Netty tcnative は arm64 向けだけ（x86_64 向けは、同じ版なら同じと見なす）。Conscrypt は 2.6.0 以降だけ（それより前は、開発元の資料から「対応していない」と見なす） |
| 確かめた範囲の外の版 | 恒久 | 確かめた範囲より新しい版は「対応が続いている」、古い版は「対応していない」と見なし、根拠を「推定」とする。今後の版で方式が外されたり、名前が変わったりすると、実際と食い違う |
| TLS で既定で使われるか | 現時点 | Bouncy Castle の TLS と Netty tcnative は、グループの定義がある（設定できる）ことを確かめただけ。既定で有効かどうかは確かめていない。Conscrypt の TLS は、開発元の資料だけが根拠 |
| ディストリが作り直した OpenSSL | 現時点 | OpenSSL は、ライブラリ本体の版の文字列で判断する。ディストリが方式を外して作り直している場合は、実際と食い違う（確かめた Debian 13 と AlmaLinux 9.8 の 3.5 系には、方式がある）。OpenSSL 3.5 より前で、別のプロバイダ（oqs-provider など）を足している場合は「未対応」と出る |

### 5.10 Tomcat

| 限界 | 区分 | 説明 |
|---|---|---|
| Tomcat が OpenSSL の実装で動く場合 | 現時点 | Tomcat の TLS の実装は、JDK のもの（JSSE）と OpenSSL のもの（Tomcat Native 経由。Ubuntu の既定）の 2 通りがあり、どちらも求める。OpenSSL の実装で求めるのは、暗号スイートと鍵交換のグループまでで、プロトコルの版は求めない（OpenSSL を使うほかのサーバーと同じ）。版ごとの既定は Ubuntu 20.04 / 22.04 / 24.04 のパッケージでだけ測っており、それ以外の組み合わせ（RHEL 系に別途入れた Tomcat Native など）は「不明」になる。証明書を複数置いた設定は、並び順で結果が変わることを確かめた版（Ubuntu 22.04 / 24.04）では「不明」とする（24.04 では RSA → EC の順だと TLS 1.3 を受け入れず、22.04 / 24.04 では後ろに書いた証明書の一部のスイートを受け入れなかった）。`cipherSuites` 属性がある場合の TLS 1.3 のスイート、TLS 1.2 を外して古い版だけを残した設定、`SSLEngine="off"` と Tomcat Native が両方ある設定も「不明」とする |
| Tomcat の対象 | 現時点 | ディストリのパッケージで導入した Tomcat（`/etc/tomcat/server.xml`、`/etc/tomcat9`〜`11/server.xml`）だけ。アーカイブを展開して置いた Tomcat（`/opt/tomcat` など）、1 台に複数ある場合の 2 つ目以降（RHEL 系の `tomcat@.service` など）、アプリに組み込まれた Tomcat（Spring Boot など）は読まない |
| Tomcat を動かす Java の特定 | 現時点 | Debian 系は `/usr/lib/jvm/default-java`、RHEL 系は `/etc/tomcat/tomcat.conf` の `JAVA_HOME` を既定とし、環境ファイル（`/etc/default/tomcat<N>`、`/etc/sysconfig/tomcat`）の `JAVA_HOME` があればそれに従う。`setenv.sh`（スクリプト）は解釈せず、あれば「不明」とする。systemd のドロップインで足された環境変数は読んでおらず、そこで `JAVA_HOME` や起動オプションを変えている場合は、結果が実際と食い違う |
| Tomcat の起動オプション | 現時点 | 環境ファイルの `JAVA_OPTS` / `CATALINA_OPTS` などに、TLS の設定を変えうる指定（`-Djava.security...`、`-Djdk.tls...`、`-Djavax.net...`、`-Djava.library.path` など）があれば「不明」とする。それ以外の場所（ドロップイン、手で書いた起動スクリプト）の指定は見ていない |
| Tomcat Native の有無の判断 | 現時点 | パッケージ（`libtcnative-1`、`libtcnative-2`、`tomcat-native`）の有無と版で判断する。パッケージ以外の方法で置かれたライブラリは分からず、その場合は JDK の実装として求めた結果が実際（OpenSSL の実装）と食い違う |
| Tomcat の証明書を複数置いた場合 | 恒久 | Tomcat は、クライアントが示したスイートの並びを見て証明書を選ぶ。そのため、RSA と EC の証明書を両方置いた場合、一覧にあるスイートでも、クライアントの示し方によっては選ばれないことがある（実測: 候補をまとめて示すと 14、1 つずつ示すと 21）。一覧は「そのスイートだけを示したクライアントがつながるか」で数えている |
| Tomcat の証明書の種類 | 現時点 | 証明書の種類は、`Certificate` の `type` 属性か、証明書ファイル（PEM）から読む。キーストア（PKCS#12、JKS）の中は読まないので、種類が分からない場合は絞り込まずに一覧を出し、確度を下げる。`groups` を書いていて EC の証明書がある場合は、証明書の曲線を読んでいないので、TLS 1.2 以下のスイートを「不明」とする |
| Tomcat の設定の書き方 | 現時点 | `server.xml` の値に `${...}`（起動時に置き換えられる値）が含まれる項目は解釈しない。`DOCTYPE` のある `server.xml` は値を求めない。属性の名前は Tomcat と同じく先頭の 1 文字だけ大文字小文字を区別しない（`ciphersuites` は `cipherSuites` と別の名前で、Tomcat も無視する）。暗号スイートの優先順（`honorCipherOrder`、`@STRENGTH` の並べ替え）は求めていない |
| Tomcat の版ごとの挙動 | 恒久 | 既定の暗号指定、語が指すスイート、`@STRENGTH` の後ろを読むか、古い書き方（Connector に直接書く TLS 設定）で起動するか、`cipherSuites` 属性が効くかは、版ごと（ディストリのパッケージごと）に違った。測った版の事実として表に持っており、測っていない版は補間（リリースだけが違う場合）か「不明」になる。同じ「10.1.x」でも、AlmaLinux 10 の 10.1.49 と Debian 13 の 10.1.60 では既定も挙動も違った |

### 5.11 Spring Boot

| 限界 | 区分 | 説明 |
|---|---|---|
| Spring Boot の対象の版 | 恒久 | 実際に起動して測った版（2.7.0〜4.1.2 の全パッチ版）だけ。それ以外の版（2.6 以前、今後出る版、スナップショットや独自ビルド）は「不明」とする。補間はしない |
| Spring Boot を測った Java | 現時点 | 測定は Ubuntu 24.04 の OpenJDK 21 だけで行った。ほかの JDK で動く場合の結果は、「Spring Boot の設定 → 同梱の Tomcat の解釈 ∩ その JDK の表」という、OpenJDK 21 で確かめた求め方をそのまま当てはめたもの。パッケージの Tomcat では、同じ求め方が Java 8 / 11 / 21 で実測と合っている |
| JAR の外からの設定の上書き | 恒久 | Spring Boot の設定は、環境変数、起動時の引数、JAR の隣や別の場所の設定ファイル、設定サーバーなどから上書きできる。起動の定義（systemd のユニット、supervisord のプログラム）の起動コマンドと環境変数、JAR の隣（と作業ディレクトリ）の設定ファイルに上書きが見つかった場合は「不明」とする。それ以外の場所での上書きは分からず、結果には「JAR の外からの上書きは確認していない」と注記する |
| Spring Boot を動かす Java の特定 | 現時点 | systemd のユニットか supervisord のプログラムの起動コマンドが、「絶対パスの java ... -jar <JAR>」の形か、JAR そのものを起動する形（そのまま実行できる JAR）のときだけ読める。自作の起動スクリプトを通すもの、init.d、ジョブ管理ツールからの起動は読めない。読めない JAR は、見つかったすべての JDK で結果が同じ項目だけ確定とする（確度は下げる）。探していない場所の JDK（アプリに同梱された JRE など）で動いている場合は、結果が実際と食い違いうる |
| Spring Boot の起動の状態 | 現時点 | 「起動するよう設定されている」と分かるのは、有効なユニットか、有効な supervisord のプログラム（`autostart=false` でないもの）から参照されている JAR だけ。それ以外の JAR は「置かれている」ことしか分からない |
| supervisord の定義 | 現時点 | 読むのは `/etc/supervisor/supervisord.conf` と `/etc/supervisor/conf.d/*.conf`（Ubuntu 24.04 の supervisor 4.2.5 で確かめた置き場）。RHEL 系の置き場（EPEL のパッケージ）、`[include]` で指定した別の場所、pip で導入した supervisord の設定は読まない。`%(...)s` の置き換えは解釈しない（コマンドにあれば起動の定義なしとして扱い、結果に関わる環境変数にあれば「不明」とする） |
| そのまま実行できる JAR | 現時点 | 先頭に起動スクリプトがある JAR は、JAR の隣の `<JAR の名前>.conf` で Java や起動時の指定が変わる。`.conf` はシェルとして実行せず、「名前=値」だけを読む。展開（`$...`）を含む値、代入でない行、TLS の設定に関わる代入があれば「不明」とする。リンクを通して起動する定義、`JARFILE` で別の JAR を指す定義も「不明」とする。`JAVA_HOME` から Java が決まらない場合（PATH の java）は、すべての JDK で結果が同じ項目だけ確定とする。起動スクリプトを差し替えたビルド（独自のスクリプトを埋め込んだ JAR）は見分けておらず、標準のスクリプトとして扱う。init.d にリンクを置いて起動する形は、起動の定義として読まない（`.conf` の内容だけ確かめる）。確かめたのは Spring Boot 2.7.18 と 3.5.16 のスクリプト（4.1.2 では付かない） |
| Spring Boot の管理用の待ち受け | 現時点 | `management.server.port` で本体と別のポートにした管理用の待ち受けは、TLS の設定（`management.server.ssl.*`、または本体の設定）がある場合に、別の待ち受けとして「不明」で記録する。TLS の設定の決まり方（本体の設定を引き継ぐかどうかを含む）は測っていないので、値は求めない。TLS の設定がどこにもない場合は記録しない |
| Spring Boot で読まない設定 | 現時点 | クラスパスの `config/` の設定ファイル（あれば「不明」とする）、`${...}` を含む値（TLS の項目なら「不明」とする）、プログラムの中で組み立てられる設定、鍵や証明書の中身を設定に直接書いたもの（書かれていたことだけ分かる） |
| Spring Boot の同梱サーバー | 現時点 | 組み込みの Tomcat だけ。Jetty、Undertow、Netty（WebFlux）を同梱するアプリは「不明」とする |
| Spring Boot の証明書の種類 | 恒久 | キーストアの中は読まないので、証明書の種類で暗号スイートを絞り込まず、確度を下げる（PEM のファイルで指定されている場合は読んで絞り込む） |
| WAR をアプリケーションサーバーに配備する形 | 現時点 | Spring Boot のアプリを WAR にして Tomcat などに配備している場合、TLS はサーバーの側の設定で決まる。WAR の中の `server.ssl.*` は使われないが、実行できる WAR として `java -jar` で起動されている場合と区別していない |

## 7. 負荷と副作用

| 限界 | 区分 | 説明 |
|---|---|---|
| 本ツールの制御外の負荷 | 恒久 | ファイルを開くことで、アンチウイルスのリアルタイムスキャン、ファイルアクセスの監査ログ、EDR の検知が発生し得る。これらの負荷や通知は本ツールの優先度・流量制限の外にある |
| アクセス時刻の更新 | 恒久 | Linux では、アクセス時刻を更新しない開き方（`O_NOATIME`）で読む。この開き方は、ファイルの所有者か root でなければ使えない。一般利用者で実行した場合、他人のファイルは通常の開き方になり、アクセス時刻が更新され得る（件数を結果の `coverage.atime_not_preserved` と警告に残す）。Linux 以外では、常に更新され得る |
| 書き込める場所の制限（Landlock） | 恒久 | 変更できる場所を出力先とログ先に限る仕組みは、Linux 5.13 以降でだけ働く。RHEL 8、Ubuntu 20.04 以前では使えず、結果に `unsupported` と記録して続ける（その場合、「出力先以外に書き込まない」は、コードの作りと seccomp の拒否リストによる） |
| 中断にかかる時間 | 恒久 | 中断（Ctrl+C、SIGTERM、SIGHUP）と `--max-duration` は、処理の区切り（ファイル、JAR、アプリなど）で止まる。1 つのファイルを読んでいる途中では止まらないので、大きなファイルや遅いディスクでは、止まるまでに時間がかかる。30 秒たっても止まらなければ、または 2 回目のシグナルで、結果を書かずに強制的に終わる（ログは残る） |
| 出力先の制約 | 恒久 | 出力先・ログ先が、探索の起点と同じか上位（`/` を含む）の場合は、エラーで終わる。上位のディレクトリに、他の利用者が書き込めるもの（スティッキービットなし。例: グループ書き込み可の `/usr/local`）がある場所も、出力先にできない |
| 流量制限の既定値 | 現時点 | CPU 使用率・読み取り速度の既定値は暫定で、負荷試験による裏付けはまだない |
| 優先度の低下 | 恒久 | 低下できない環境では、警告を記録して処理を続ける |

## 8. 出力について

| 限界 | 区分 | 説明 |
| レポートに埋め込む CBOM | 恒久 | レポートには、ホストごとの CBOM を埋め込む（保存用のリンク）。その分ファイルが大きくなる。合計 48 MB を超える分のホストには埋め込まない。レポートを渡すことは、CBOM を渡すことでもある |
|---|---|---|
| 出力は機微情報を含む | 恒久 | 秘密鍵やパスワードの値は含まないが、ファイルパス、ホスト名、証明書の Subject、ソフトウェアの版などを含む。出力ファイルは作成者だけが読める権限で作るが、その後の取り扱いは利用者の責任 |
| ハードリンクも「上書きしない改名」も使えない出力先 | 恒久 | 結果ファイルは、既存のファイルを上書きしない方法（ハードリンク、または上書きしない改名）で確定する。どちらも使えない出力先では、スキャンの前にエラーで止まる。Linux 以外では「上書きしない改名」に対応していないため、ハードリンクを作れないファイルシステム（vfat、exfat など）には出力できない |
| ハードリンクを作れないファイルシステムでの確認 | 現時点 | vfat / exfat を実際にマウントした環境での確認は未実施（上書きしない改名そのものは、実際のカーネルで動作を確認した） |
| 出力先の権限 | 恒久 | グループや他のユーザーが書き込める出力先、実行ユーザーと root 以外が所有する出力先は拒否する |
| CSV は情報量が落ちる | 恒久 | 出現1件1行に平坦化するため、キーストアの詳細やリンク関係などは含まれない |
| データ形式は未確定 | 現時点 | 結果 JSON の形式は v0 で、互換性を保証しない |
| CBOM は情報量が落ちる | 恒久 | CBOM（CycloneDX 1.6）への変換では、CycloneDX に対応する欄がない情報（判定、利用の確からしさ、確度、特定できなかった理由など）を、名前が `kagiya:` で始まる独自のプロパティに入れる。ほかのツールがこれを解釈するとは限らない。設定の記載そのもの、求め方の過程、OS の暗号設定、読み飛ばしの記録は含まれない。情報の正本は結果 JSON |
| CBOM の種別の対応づけ | 恒久 | CycloneDX の種別（`primitive`）への対応は、このツールの判断による。署名にも鍵共有にも使われる鍵（EC など）と曲線は `other`、鍵交換のグループと SSH の鍵交換は判定がハイブリッドなら `combiner` とする。暗号スイートは OpenSSL での名前で出し、IANA の識別子と、構成するアルゴリズムへの参照は付けていない |
| CBOM の判定 | 恒久 | CBOM に入る判定は、結果ファイルの中の判定（スキャンした時点の評価ポリシー）。HTML レポートは作る時点の評価ポリシーで判定し直すため、評価ポリシーを更新したあとは、両者が食い違うことがある |
| CBOM の検証の範囲 | 現時点 | 公式のスキーマ（1.6）に適合することは実物の結果で確かめたが、個々の CBOM 対応ツールに取り込めることは確かめていない |

## 9. 評価とレポートについて

| 限界 | 区分 | 説明 |
|---|---|---|
| 評価は目安 | 恒久 | 判定は、評価ポリシーが根拠にした文書（NIST IR 8547、CRYPTREC 暗号リストと暗号強度要件、RFC 8996、RFC 9142）に照らした目安。個々のシステムで移行が必要か、いつまでに行うかは、扱う情報と利用期間に応じて利用者が判断する。文書が改定されれば、ポリシーの更新が要る |
| 文書によって扱いが違うもの | 恒久 | AES-128 と SHA-256 は、CRYPTREC の耐量子計算機暗号リストに載っていないため「量子計算機で強度が下がる」と判定する。NIST は置き換えを求めていない。どちらの基準で見るかで結論が変わる |
| 文書に記載のない方式 | 恒久 | 参照した文書に記載のない方式（ARIA、SEED、IDEA、UMAC、bcrypt など）と、暗号カタログにない方式は「判定できない」とする。安全とも危険とも言っていない |
| TLS 1.3 の鍵共有 | 恒久 | TLS 1.3 の暗号スイートそのものは、量子計算機に対する評価を「判定できない」とする。鍵共有はスイートではなく鍵交換のグループで決まるため、同じ範囲の「鍵交換のグループ」の欄で判定する。TLS 1.2 以下の ECDHE / DHE のスイートは、スイートの欄では一律に「量子計算機に弱い」とする（TLS 1.2 では耐量子のグループは使われない） |
| 自己署名のルート証明書の署名方式 | 現時点 | 証明書は、鍵と署名の方式のうち厳しいほうで判定する。信頼の起点になるルート証明書の自己署名は安全性に影響しないが、区別せずに判定している（SHA-1 で自己署名された古いルート証明書が「危殆化」と出る） |
| 証明書の判定に使う情報 | 恒久 | 証明書の判定は、鍵の種類と長さ、署名の方式による。用途、発行元の信頼性、失効、名前の一致は見ていない |
| 評価の対象になる設定値 | 現時点 | 設定のうち評価するのは、実効値を求められた項目（暗号スイート、鍵交換のグループ、SSH の各方式）と、設定に書かれた TLS のプロトコルの版。署名アルゴリズムの設定、外向きの接続の設定は評価していない |
| 要点の数え方 | 恒久 | 要点の数は、サービス・範囲ごとに受け入れる設定になっている方式の延べ数。同じ方式が複数の範囲で許可されていれば、その数だけ数える。見つかったサービスはすべて数える（起動するよう設定されているかどうかは、各サービスの欄に示す）。「量子計算機に弱い方式」の内訳の「鍵交換」と「署名・認証」は、1つの暗号スイートが両方に数えられることがある |
| 期限の判定 | 恒久 | 証明書の期限切れ・期限間近は、スキャンした時点を基準に判定する。レポートを開いた日ではない |
| レポートの規模 | 現時点 | 複数ホストをまとめたレポートは、ホストごとの詳細をすべて 1 つの HTML に入れる。入力は 200 ファイルまで。数百〜数千ホストを扱う集約（`merge`）は未実装 |
| レポートの言語と操作 | 現時点 | 日本語のみ。スクリプトを使わないため、並べ替えや絞り込みはできない（ブラウザの検索を使う）。表示の切り替え（全体の集計とホストごとの詳細）はスタイルシートの機能（`:target`、`:has()`）で行うので、これらに対応していない古いブラウザでは切り替わらない。印刷するとすべてのホストの詳細が出る |
| 「設定からの参照を確認できなかった秘密鍵」 | 恒久 | このツールが読んだ設定（対応しているサービスの設定ファイル）から参照が見つからなかった、という意味にとどまる。対応していないアプリケーションや、調べていない場所から使われている可能性があり、使われていないことの根拠にはならない |
| 「探索した範囲」の示し方 | 恒久 | レポートは探索の起点と、その下で読み飛ばしたもの（権限がなく読めなかったものなど）を示す。起点の外にあるもの（利用者のホームディレクトリなど）は挙げない。「調べていない場所」の全体は示せない |
| パッケージの版を変えずに行われた変更 | 現時点 | 判定は、導入されているパッケージの版で実測した挙動に基づく。版を変えずに中身が差し替えられている場合（独自にビルドしたプログラムへの置き換え、`LD_PRELOAD`、環境変数での設定の差し替え）は検知できない。パッケージ管理データベースが持つ配布物のハッシュとの照合は未実装（追加開発の候補） |

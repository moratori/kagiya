# 要件（ユーザー提示の原文）

PQC移行は、初手としてクリプトインベントリを作成することが重要だと思います。
クリプトインベントリ作成ツールを開発したいです。

以下に大枠の要件をお示しするので、詳細要件は以下の記載からあなたの判断で導出し、決定していただいて構いません。重要と思われる部分については、相談を仰いでいただければと思います。

# 大方針

- PQC移行時につくって終わりではなく、将来の暗号危殆化に備え、AESなどCRQCの影響を直近受けないとされるアルゴリズムも網羅的に管理できるようにする。

- 日系の大企業など、多くのシステムを管理している組織で導入しやすいようにする。

- ネットワーク通信は一切行わず、本ツールが稼働するシステムの情報を読み取りで完結すること。(非常に重要)

- 既存のクリプトインベントリ作成ツールが苦手とする部分をカバーするようにする。
  - クラウド事業者が提供しそうな機能は省くこと。(クラウドのKMSなどは、そっち側でインベントリ作成できそう)

# 方向性

- 新たな暗号が登場した時に簡単に追加できること。

- 複雑な構成（ツールプロセス間で通信を行うなど）を避け、シンプルにすること。

- 仮に本番環境で実行された場合でも問題が生じづらくするように、システムに負荷をかけない設計とすること。

- 本ツール自身が、セキュリティ上のバックドアにならないよう注意すること。

- ツール自体は単一の実行可能ファイルとすること。(追加のランタイムを必要としない、OSごとの単一実行ファイル。)

# 禁止事項

- 出力先ディレクトリ以外に書き込まない
- ポートを待ち受けない。外部と通信しない
- ネットワークスキャンは行わない。
- ネットワーク通信を行わない。
  - NFSや、Sambaなどネットワークファイルシステムを読み込まないように注意してください。これらの読み込みをスキップしたことを記録に残してください。
  - 証明書チェーン検証、XMLの外部参照、名前解決など、暗黙に通信が発生する処理に注意してください。
- 秘密鍵・パスワード等の値を出力・ログに含めない（アルゴリズム、鍵長、フィンガープリント等のメタデータのみ）
- 自動アップデートやテレメトリを実装しない
- 出力ファイルは機密扱いとし、作成者以外が読めない権限で作成する
- CPU優先度を下げて動作しすること。

# スキャンについて

本ツールが稼働するシステムの情報を読み取りで完結すること。ネットワークスキャンは行わない。

- 各種サーバーアプリケーション（例：Nginx, apache, postfix...など無数)の設定ファイルの確認
  - サーバーアプリケーションのバージョンを考慮し、正しいものを読み取ること。
  - また、実際に使われる暗号は「アプリの設定 ＞ OSの暗号ポリシー ＞ ライブラリのデフォルト」の順で決まるため、
    設定ファイルに明記されていない値もこの順で解決すること。
- 証明書ストア
  - OS標準のストア以外に、アプリ特有のストアがあることを考慮すること
- OSの暗号設定
  - Windowsのレジストリ、Linuxのシステム全体の暗号ポリシーなど
- 指定されたディレクトリのソースコード解析
  - Java、VB.NET、PowerShell、シェルスクリプトは対象にしてください。
  - 各言語の著名な暗号ライブラリ(例：BouncyCasle)のAPIに対応できるようにしてください。
  - これらの言語でよく使われる設定ファイルのうち、暗号関連を記載するものがあればそれも対象としてください。application.propertiesなど。
  - コードの記載スタイルに惑わされないように、なんらかの正規化をした上でチェックしてください。
  - ソースコードの深いデータフロー解析は行わなくて良いです。
- バイナリファイルのアプリケーション
  - ELFの動的セクション／PEのインポート表、静的リンクされたライブラリのバージョン文字列、Javaクラスファイル内のアルゴリズム名を読むイメージです。
  - ELFやPEの逆コンパイル・逆アセンブルは行わないでください。

- 読み取り権限がない場合は、それをログに記録してください。
- スキャン除外のオプションを設けられること。（ファイルパスなど）

- 検出ルールは定義ファイルとして分離可能とするが、引数で明示的に指定された場合のみ読み込む。検出ルール定義ファイルを読み込まない場合は、ツールが内包するルールに従う。既定のルールを書き出す場合は、専用のサブコマンドでオプションで指定された出力先ディレクトリに書き出す。

# 出力について

- 汎用的なフォーマットを扱えること。CBOM, JSON, CSVなど
  - 今回の要件を達成するために独自のスキーマでJSONを定義しても構いません。（多分JSONが一番表現力が高いため）そこから、CBOMやCSVに情報量を落としてもよいので、変換できるようにしてください。

- 可視化機能を設ける。
  - スキャン結果のファイルを引数にして起動することで、ヒューマンフレンドリーな綺麗なデザインの単一のhtmlファイルを出力すること。デフォルトではカレントディレクトリ。オプション指定がある場合はそこ。（別途ブラウザを人間が手動で開いてhtmlファイルを見る。htmlを配信するためのWebサーバを設けてはいけない）
  - 複数のスキャン結果ファイルを入力することも可能とし、それに応じた適切なデザインの出力htmlを出力すること。

- カレントディレクトリにログフォルダを作成し、そこに出力してください。オプションで指定がある場合は、そこをログ出力フォルダとすること。

# 動作環境

- windows, windows server, linuxを動作環境とすること
- linuxについては、主要なディストリビューションで動作する可能性があり、システム構成を考慮すること
  - RHEL、ubuntuは含むこと。
- osのバージョンを考慮すること
  - RHEL 8以降、Windows Server 2016以降、ubuntu 16.04以降

# 進め方

- 実装に入る前に設計書（対象、データモデル(入力、出力、検出ルールなど)、構成、言語の選定理由、フェーズ計画）を作成し、独立したエージェントのクリティカルレビューを受けること。

- 相談事項があれば、ユーザーに相談すること
